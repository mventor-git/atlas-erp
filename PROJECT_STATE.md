# Atlas ERP Project State

**As of:** 2026-09-25
**Phase:** Partial standalone business slice with durable connected-sale idempotency. `Business` covers purchasing -> stock and a local manual cash sale -> stock -> balanced cash/revenue journal path, and exposes immutable typed read projections through a narrow authenticated loopback HTTP profile. A connected peer can post one manual sale through that profile, and the *receipt* of an accepted connected sale now survives a restart in a real PostgreSQL table. A reproducible example database (`db/`) now also ships a fictional six-product catalogue for local work; it is not the contract's `atlas_erp` database and no application code reads it. A first browser surface now exists as well: `atlas_erp/web.py` serves a read-only, dependency-free console on loopback that renders the example catalogue and the domain's own sales, stock, and journal state. It is a demo over the committed seed fixture, not a product surface. Acceptance gate 1 remains partial, acceptance gate 2 is not met by that console, acceptance gate 3 is not fully demonstrated, and the product is still in progress.

## Implemented

- Python package with a local `core -> cluster -> plugin -> module` registry and no runtime third-party import on the standalone paths. The six baseline ERP clusters are seeded, and registrations and manifests are validated. `psycopg` is now a declared dependency, but it is imported only inside the sale-store adapter, so the package still imports and runs when the driver is absent.
- Process-local Atlas Connect kernel covering major-version handshake, manifest validation, share-only pairing, explicit `master`/`reader`/`proposer` authority, snapshots with opaque cursors, ordered deltas, idempotent inbox handling, and proposal transitions.
- In-memory `Business` domain for master items, purchase orders, receipts, and stock. Receiving an order once derives stock and rejects duplicate receipts; the local registry exposes `masterdata.items`, `purchasing.purchase_orders`, and `inventory.stock` without a peer.
- Local manual cash-sale flow that validates stock, decrements it, and records immutable `Sale`, `JournalEntry`, and `StockMovement` values. The journal is deliberately cash/revenue only: cash is debited and revenue is credited for the sale total. The local registry also exposes `sales.manual_sales` and `finance.journals` without a peer.
- `StockLevel` and `AuditSnapshot` are immutable, typed read projections over the item master, stock, sales, journals, and stock movements. The audit payload carries a typed item master (`item_id`, `sku`, `name`, `price_cents`) alongside the existing collections, so a peer can learn ERP-owned identity and price without a separate read. `Business.audit_snapshot()` orders items and stock by item ID, preserves recorded order for the other collections, and returns a point-in-time view that cannot observe later mutations; the projection remains in memory.
- `atlas_erp.connect_server` is a loopback-only HTTP profile: `GET /health` is public, while `GET /connect/manifest`, `GET /connect/audit`, and `POST /connect/sales` require a bearer token supplied by `ATLAS_ERP_CONNECT_TOKEN`, and every route refuses a non-loopback peer. The manifest wire response normalizes permissions to a sorted flat array, and the audit response is a typed snapshot with a deterministic cursor.
- `POST /connect/sales` validates a bounded JSON body, checks every submitted `unit_price_cents` against the local item master (`400 price mismatch`), then calls the same `Business.create_manual_sale` path the local console would, so stock and journal invariants still hold. It never retries on the caller's behalf. The `201` response returns the posted sale, its journal ID, the resulting stock, and `journal_balanced`, so a peer can validate what it was handed without a second read. `409 insufficient stock` covers a stock conflict and `409 duplicate sale` covers a repeated `sale_id` rejected by the in-memory domain. Internal failures return a generic `500` and never leak detail.
- `atlas_erp.sale_store` is the durable idempotency layer for that one command. One `SaleCommandStore` protocol declares `reserve` / `complete` / `abort` / `close`, with two adapters: `InMemorySaleCommandStore` for tests and the loopback smoke, and `PostgresSaleCommandStore` for cross-process durability. The store owns exactly one table, `connected_sale_commands` (`sale_id` primary key, `request_hash`, a `status` check limited to `pending`/`completed`, a `response` jsonb receipt, `reserved_at`, `completed_at`). It is explicitly *not* an ERP state store: the item master, stock, sales, and journals stay in the in-memory `Business` domain.
- `sale_command_hash` defines the identity of one connected sale command as a SHA-256 over the *validated* request (`customer_id`, `sale_id`, `lines`) serialized canonically, so JSON key order and insignificant whitespace do not change a command's identity while a different sale, customer, quantity, or price does.
- `ConnectServer(..., sale_store=...)` takes the store optionally. With one injected, `POST /connect/sales` reserves the `sale_id` before touching the domain and then completes it with the receipt: an identical retry replays the stored receipt and returns `201` without calling the domain again, the same `sale_id` with a different request is `409 sale id conflict`, an unfinished reservation is `409 sale in progress`, and any failure between the two calls aborts the reservation so a rejected sale never burns its key. With no store injected, behaviour is unchanged and the in-memory `409 duplicate sale` still applies.
- `ATLAS_ERP_DATABASE_URL` wires the durable store in the `atlas_erp.connect_server` entry point: unset or blank keeps the in-memory store, a usable value creates the table and reports `sale receipts: postgres`, and a configured-but-unusable database is a startup failure rather than a silent downgrade to a store that does not survive a restart. Only the variable name is reported on failure, never the connection string. `psycopg` is declared in `pyproject.toml` but imported inside the adapter, so the package still imports when the driver is absent.
- `tests/cross_process_smoke.py` is a one-shot harness that starts one temporary ERP loopback server and then runs three Ecom clients against it: the read-only `connect:smoke`, the durable `connect:checkout-smoke` with `ATLAS_ERP_ALLOW_WRITE=1` (skipped with a printed reason when `ATLAS_ECOM_DATABASE_URL` is unset), and the lower-level `connect:order-smoke`. Child process cleanup is in `finally`. It is test infrastructure, not full pairing, full connected business operation, or production persistence.
- `python -m atlas_erp` standalone smoke entry point remains available and exercises purchasing -> stock and manual sale -> stock -> journal. The business and protocol state are process-local test infrastructure.
- `atlas_erp/demo_catalog.py` is the console's fixture: an immutable in-memory mirror of the committed `db/seed.sql` example catalogue (six items, 37 colour/size variants, one Unsplash placeholder image per variant, per-warehouse on-hand/reserved stock, two warehouses, two suppliers, two purchase orders) with the seed's own derived variant identity (`<SKU>-<COLOR>-<SIZE>`), plus `to_dict()` for the JSON route. It reads no table, and `tests/test_web.py` diffs it against the committed seed so a drift between fixture and seed fails the suite.
- `atlas_erp/web.py` is a server-rendered console built on the standard library only: no framework, no build step, no external CSS or JavaScript, and no new runtime import. `python -m atlas_erp.web` binds `127.0.0.1` on `ATLAS_ERP_WEB_PORT` (default `4311`, which leaves the Connect API on `4310` usable at the same time) and serves `GET /` as the HTML dashboard, plus `GET /api/health`, `GET /api/catalog`, and `GET /api/audit`. The dashboard is tiles, per-item catalogue cards with the variant table, stock by warehouse, purchasing, and the recent sales and general-ledger rows. `/api/health` and `/api/catalog` state `demo-fixture` and their `db/seed.sql` source so a reader cannot mistake fixture state for the real database, and `/api/audit` returns the same typed `AuditSnapshot` the Connect profile serves rather than a second truth.
- The console is read-only and demo-only. There is no host knob, so it cannot be bound to a network; an unknown route is `404`, any other method is `405` with an `Allow` header, and an internal failure answers a generic `500` that leaks no detail. Responses carry `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that permits only the seed's image host, every interpolated value is HTML-escaped, and the document contains no script at all. Its state is `build_demo_business`: it registers the fixture items, receives the seed's one *received* purchase order, and posts three deterministic manual sales through the real `Business` methods, so the stock, sales, and journals on the page are the domain's own output, and the open purchase order stays genuinely open. All of it is rebuilt on every start and gone on exit; nothing is read from or written to a database and no peer is involved.
- `db/` is a reproducible example database, not production persistence. `db/schema.sql` creates eight `example_*` tables and `db/seed.sql` loads six fictional products with 37 colour/size variants (colour-only for the one-size products, colour x size for the rest), exactly one image row per variant, stock per variant across two warehouses, plus ERP-local suppliers and two purchase orders. Every statement is `CREATE TABLE IF NOT EXISTS` or `INSERT ... ON CONFLICT`, and the README's suggested database name is deliberately *not* `atlas_erp` so example data can never be confused with the real database the contract reserves. `db/README.md` documents the load order, the shared identity contract with `atlas-ecom`, and the verification queries. Nothing in the package reads these tables: the only table the application owns is still `connected_sale_commands`.
- `.gitignore` covers `__pycache__/`, `*.pyc`, `.env` (a local `ATLAS_ERP_DATABASE_URL`), and `*.dump`, while leaving `db/*.sql` versioned on purpose. No ignore rule hides a tracked source file.

## Explicitly deferred

- The operator console is a read-only demo, so acceptance gate 2 is not met. `atlas_erp/web.py` renders fixture and in-memory state and offers no write surface at all: an operator cannot create, edit, receive, or acknowledge anything from the browser, and there is no authentication, no session, no CSRF token, and no audit of who looked. Anything a browser could change today would change only state a restart discards. A real console needs the ERP-owned database first, then an authenticated operator write path.
- Full ERP persistence. Only the command receipt is durable. The item master, stock, sales, journals, audit history, and the protocol adapter all remain in memory and are lost on restart, so duplicate-sale *detection* survives a restart but the sale itself does not: a retried `sale_id` after a restart replays the original `201` receipt while the audit snapshot no longer contains that sale, and the peer's sale id now points at a sale ERP has forgotten. A real `atlas_erp` database per the contract's ownership rule, durable inbox/outbox, and durable audit history are not implemented. The console makes this visible rather than fixing it: the page it renders is gone on exit.
- The real `atlas_erp` schema. `db/schema.sql` is explicitly not it: every object is `example_`-prefixed example data, there is no migration runner, no migration history, and no down-migration, and no code reads those tables. Building the contract's ERP-owned schema and pointing the business domain at it is a later decision, not something this dataset does.
- Crash recovery for a stuck reservation. A process that dies between `reserve` and `complete` leaves a `pending` row that is answered `409 sale in progress` forever, because `reserved_at` carries no lease or expiry. This is a deliberate ceiling: recovering a crashed attempt needs a lease or timeout, which is worth adding only once a real crash is in scope.
- Connection handling. `PostgresSaleCommandStore` holds one connection behind one lock, so concurrent requests serialise; a pool belongs with the real database work, not this slice.
- The console's demo fixture is not masterdata. `atlas_erp/demo_catalog.py` mirrors the committed example rows so a browser can be pointed at something, and the item master the console renders for variant availability is a second, item-level view of the same numbers rather than the domain's own stock. The variant image links are the same Unsplash placeholders the seed carries, so the licence review below covers what the console shows.
- Full Connect pairing and connected-mode transport, one-time-code and scoped-credential exchange, full conformance, and real degradation/resynchronization. The current endpoints are a narrow loopback profile; acceptance gate 3 is not fully demonstrated. The console is also a standalone-only surface: it has no peer connection and no connected presentation, and it deliberately runs on a different port from the Connect API so the two never share a process.
- Full Ecom order synchronization, authority/import behavior, and connected presentation. The connected write is a manual-sale command, not Ecom order synchronization, and there is no durable outbox or resynchronization story.
- TLS, hardened authentication, network exposure, and production security controls. The bearer token is read from an environment variable and compared with a constant-time compare, which is not a production security boundary.
- Payments, COGS, accounts receivable, and tax. The current journal is intentionally cash/revenue only and is not a complete accounting implementation.
- Ecom storefront and `ecom-manager` UI are outside this product's boundary and are not implemented here. The sibling `atlas-ecom` repository now carries its own demo storefront and manager, which are equally in-memory and connect to nothing, so the two consoles cannot be mistaken for one integrated system.
- Licensing and attribution for the example imagery. The 37 image rows point at 13 shared `images.unsplash.com` CDN links as placeholders, no image files are committed, and this repository carries no photographer attribution. Linking a CDN URL is not the same as being licensed to sell the photograph, so before any real deployment each photo needs the normal Unsplash licence review, per-photographer attribution where the photographer has asked for it, the API terms if the links ever switch to the API, and a decision between remote links and self-hosted assets. That review is product work and has not been done.

## Next safe slice

The branch is published and in step with `origin/main`, but the working tree now carries the uncommitted console slice, so the immediate next step is a repository decision before more code: commit and push that slice as it stands, then return to code rather than to the repository. Make the durable layer cover the state it is closest to, not the whole domain. Add a lease or expiry on `reserved_at` so a crashed attempt cannot hold a `sale_id` forever, and make the `in_progress` answer say how long the caller should wait. That is a bounded change to the one table ERP already owns, and it is the last known way a retry can be permanently refused. Only after that, decide explicitly whether ERP's business state should follow the receipt into a real `atlas_erp` database, because the receipt currently promises a sale that a restart forgets. Keep the standalone paths, the in-memory store default, and the loopback profile stable, and defer the full database, the real operator console with its authenticated write path, payments, TLS, full pairing, authority/import, and full Ecom order synchronization until the receipt and the facts behind it agree. Treat `db/` as loadable example data that must be kept in step with the `atlas-ecom` seed in the same commit whenever the shared catalogue identity changes, and re-verify the seeds after any such change because the `atlas-seed-check` container that verified them is gone.

The console also changes what is worth doing next after that commit, and the order matters. Because the console currently reads in-memory state that no restart keeps, spend the next UI slice on a *durable* read surface rather than more rendering: point the item master, stock, sales, and journals at the contract's real `atlas_erp` database, and let the console read those, so a sale an operator can see is a sale that survived the process. Only after that does a write button belong on the page, and it should go through the same `Business` methods the Connect profile already calls, behind an authenticated operator session with an audit record. Until the data is durable, a browser action would only edit state that disappears, which is a worse demo than a read-only one. Two smaller obligations come with the fixture: `atlas_erp/demo_catalog.py` has to be updated in the same commit as any `db/seed.sql` change, because `tests/test_web.py` fails on drift, and the Unsplash links the console renders are the same placeholders covered by the licensing review above.
