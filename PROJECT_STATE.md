## Implemented

- Python package with a local `core -> cluster -> plugin -> module` registry and no runtime third-party import on the standalone paths. The six baseline ERP clusters are seeded, and registrations and manifests are validated. `psycopg` is now a declared dependency, but it is imported only inside the two store adapters, so the package still imports and runs when the driver is absent.
- Process-local Atlas Connect kernel covering major-version handshake, manifest validation, share-only pairing, explicit `master`/`reader`/`proposer` authority, snapshots with opaque cursors, ordered deltas, idempotent inbox handling, and proposal transitions.
- In-memory `Business` domain for master items, purchase orders, receipts, and stock. Receiving an order once derives stock and rejects duplicate receipts; the local registry exposes `masterdata.items`, `purchasing.purchase_orders`, and `inventory.stock` without a peer.
- Local manual cash-sale flow that validates stock, decrements it, and records immutable `Sale`, `JournalEntry`, and `StockMovement` values. The journal is deliberately cash/revenue only: cash is debited and revenue is credited for the sale total. The local registry also exposes `sales.manual_sales` and `finance.journals` without a peer.
- `StockLevel` and `AuditSnapshot` are immutable, typed read projections over the item master, stock, sales, journals, and stock movements. The audit payload carries a typed item master (`item_id`, `sku`, `name`, `price_cents`) alongside the existing collections, so a peer can learn ERP-owned identity and price without a separate read. `Business.audit_snapshot()` orders items and stock by item ID, preserves recorded order for the other collections, and returns a point-in-time view that cannot observe later mutations; the projection remains in memory.
- `atlas_erp.connect_server` is a loopback-only HTTP profile: `GET /health` is public, while `GET /connect/manifest`, `GET /connect/audit`, and `POST /connect/sales` require a bearer token supplied by `ATLAS_ERP_CONNECT_TOKEN`, and every route refuses a non-loopback peer. The manifest wire response normalizes permissions to a sorted flat array, and the audit response is a typed snapshot with a deterministic cursor.
- `POST /connect/sales` validates a bounded JSON body, checks every submitted `unit_price_cents` against the local item master (`400 price mismatch`), then calls the same `Business.create_manual_sale` path the local console would, so stock and journal invariants still hold. It never retries on the caller's behalf. The `201` response returns the posted sale, its journal ID, the resulting stock, and `journal_balanced`, so a peer can validate what it was handed without a second read. `409 insufficient stock` covers a stock conflict and `409 duplicate sale` covers a repeated `sale_id` rejected by the in-memory domain. Internal failures return a generic `500` and never leak detail.
- `atlas_erp.sale_store` is the durable idempotency layer for that one command. One `SaleCommandStore` protocol declares `reserve` / `complete` / `abort` / `close`, with two adapters: `InMemorySaleCommandStore` for tests and the loopback smoke, and `PostgresSaleCommandStore` for cross-process durability. The store owns exactly one table, `connected_sale_commands` (`sale_id` primary key, `request_hash`, a `status` check limited to `pending`/`completed`, a `response` jsonb receipt, `reserved_at`, `completed_at`). It is explicitly *not* an ERP state store, and it still is not one: it owns the receipt and nothing else. What it names used to be an incoherence, because the `Sale` it replays lived only in `Business._sales` — after a restart the receipt replayed a `201` naming a sale `/connect/audit` no longer listed and `stock_for` no longer reflected. The next bullet is what closed that, and this store is unchanged by it.
- `atlas_erp.business_store` is the durable layer for the business state a connected sale produces, and it mirrors `sale_store.py`'s shape deliberately rather than inventing a second one: a `BusinessStore` protocol (`ensure_schema` / `load` / `save_item` / `save_sale` / `save_movements` / `close`), an `InMemoryBusinessStore` for tests and the loopback smoke, a `PostgresBusinessStore` for cross-process durability, and a frozen `BusinessRecords` type whose field names are exactly `Business.restore`'s keyword arguments, so a load result is handed to the domain without reshaping. It owns six tables: `master_items`, `sales` + `sale_lines`, `journal_entries` + `journal_lines`, and `stock_movements`. **Two rules make the round trip honest rather than merely plausible, and both are load-bearing.** *Order is stored, not derived*: the domain has no clock and no sequence of its own — `audit_snapshot` reports sales, journals, and movements in raw `dict` insertion order, which is process memory and nothing else — so every table carries a `bigserial seq` and `load()` reads `ORDER BY seq`. Ordering by business id instead would be wrong, and `tests/test_business_store.py` proves it with three sale ids (`…-sale-later`, `…-sale-audit`, `…-sale-json`) that no alphabetical sort reproduces. *No derived value is stored*: there is no stock column and no `total_debits_cents` column anywhere, because `stock_for` and `JournalEntry` totals re-derive from lines and a stored copy would drift from the lines it was copied from; the PostgreSQL test reads `information_schema` and asserts no such column exists and that every `*_cents` column is `bigint`. Money is integer cents in a `bigint` and never becomes a float. Table and column names are module-level literals, so no caller-supplied value ever reaches an identifier, and `psycopg` is imported function-locally so the package still imports without the driver — `PostgresBusinessStore` raises only when it is constructed. **Purchasing is deliberately not stored yet**: there is no `purchase_orders` and no `receipts` table, so a reloaded domain has `receipt:receipt-1:0` and its siblings — stock movements with no `Receipt` and no `PurchaseOrder` behind them. That gap is recorded at full length below rather than footnoted here.
- `Business.restore(...)` is the single additive rehydration entry point, plus a module-level `_restored` helper that refuses to collapse a duplicate key instead of silently losing the record — the failure mode a rehydration path is most able to hide. `business.py` is **121 insertions and 0 deletions**, verified, so no existing signature, behaviour, or exception changed and every pre-existing test passes untouched. It repopulates the private dicts in the order it is given, because the order *is* the audit order; it rebuilds the two derived indexes `_items_by_sku` and `_receipts_by_order` rather than trusting them, since a reload that skipped them would lose SKU uniqueness and make `get_receipt_for_order` answer `None`; and it goes through the frozen dataclasses' own constructors so an invalid stored record fails loudly during reload instead of yielding a wrong number later, with nothing assigned until every record is built, so a rejected reload leaves the previous state intact. `_receipts_by_order` is derived from the receipts' own `order_id`, so it rebuilds even with no purchase order present.
- `ConnectServer(..., business_store=...)` takes the second store optionally, as a trailing keyword defaulting to `None`, threaded through `_make_server` and `_ConnectHTTPServer`, so every existing caller is unaffected and `ConnectServer.close()` closes it alongside the sale store. `POST /connect/sales` writes the posted sale, its journal, and its movements through **before** `store.complete(...)` and inside the same `try`, so a store that cannot record the sale aborts the key and the peer is never handed a `201` for a sale no restart would still know about. The movements are read back off the domain rather than rebuilt, so the durable `movement_id`s are the ones the domain itself minted. The entry point reads the same `ATLAS_ERP_DATABASE_URL` on exactly the sale store's terms — blank or unset means in-memory, present-but-unusable is a startup failure naming the variable and never the DSN — and the banner now reports both modes, e.g. `sale receipts: postgres, business state: postgres`. The new helpers are `_sale_movements`, `_write_business_state`, `_business_store`, `_seed_business_store`, and `_startup_business`. `_startup_business` is where the restart actually happens: with no store it is the in-memory smoke fixture unchanged; with one, **stored state wins** — an empty store is seeded from the fixture once, and a populated store is restored instead of the fixture.
- `atlas_erp.web`, `atlas_erp.demo_catalog`, `__main__.py`, and `protocol.py` were **not touched** by this slice, and the constraint the console tests enforce on the first two (neither may contain `psycopg` or `sqlite`) still holds — the grep returns no match. The console therefore remains a demo-fixture reader by design, not by omission, and `web.py` is unaffected by the store's existence. `AuditSnapshot.to_dict()` still emits exactly the same five keys, so the wire contract with the React console and the content-hash cursor are both unchanged and the sibling `atlas-ecom` repository needs no change from this slice.
- `sale_command_hash` defines the identity of one connected sale command as a SHA-256 over the *validated* request (`customer_id`, `sale_id`, `lines`) serialized canonically, so JSON key order and insignificant whitespace do not change a command's identity while a different sale, customer, quantity, or price does.
- `ConnectServer(..., sale_store=...)` takes the store optionally. With one injected, `POST /connect/sales` reserves the `sale_id` before touching the domain and then completes it with the receipt: an identical retry replays the stored receipt and returns `201` without calling the domain again, the same `sale_id` with a different request is `409 sale id conflict`, an unfinished reservation is `409 sale in progress`, and any failure between the two calls aborts the reservation so a rejected sale never burns its key. With no store injected, behaviour is unchanged and the in-memory `409 duplicate sale` still applies.
- `ATLAS_ERP_DATABASE_URL` wires the durable stores in the `atlas_erp.connect_server` entry point: unset or blank keeps both in memory, a usable value creates both sets of tables and reports `sale receipts: postgres, business state: postgres`, and a configured-but-unusable database is a startup failure rather than a silent downgrade to a store that does not survive a restart. One variable, two stores over one URL, which is deliberate: they own different tables and merging them into one transaction is a later slice. Only the variable name is reported on failure, never the connection string. `psycopg` is declared in `pyproject.toml` but imported inside each adapter, so the package still imports when the driver is absent.
- `tests/cross_process_smoke.py` is a one-shot harness that starts one temporary ERP loopback server and then runs three Ecom clients against it: the read-only `connect:smoke`, the durable `connect:checkout-smoke` with `ATLAS_ERP_ALLOW_WRITE=1` (skipped with a printed reason when `ATLAS_ECOM_DATABASE_URL` is unset), and the lower-level `connect:order-smoke`. Child process cleanup is in `finally`. It is test infrastructure, not full pairing, full connected business operation, or production persistence.
- `python -m atlas_erp` standalone smoke entry point remains available and exercises purchasing -> stock and manual sale -> stock -> journal. The business and protocol state are process-local test infrastructure.
- `atlas_erp/demo_catalog.py` is the console's fixture: an immutable in-memory mirror of the committed `db/seed.sql` example catalogue (six items, 37 colour/size variants, one Unsplash placeholder image per variant, per-warehouse on-hand/reserved stock, two warehouses, two suppliers, two purchase orders) with the seed's own derived variant identity (`<SKU>-<COLOR>-<SIZE>`), plus `to_dict()` for the JSON route. It reads no table, and `tests/test_web.py` diffs it against the committed seed so a drift between fixture and seed fails the suite.
- `atlas_erp/web.py` is a server-rendered console built on the standard library only: no framework, no build step, no external CSS or JavaScript, and no new runtime import. `python -m atlas_erp.web` binds `127.0.0.1` on `ATLAS_ERP_WEB_PORT` (default `4311`, which leaves the Connect API on `4310` usable at the same time) and serves `GET /` as the HTML dashboard, plus `GET /api/health`, `GET /api/catalog`, and `GET /api/audit`. The dashboard is tiles, per-item catalogue cards with the variant table, stock by warehouse, purchasing, and the recent sales and general-ledger rows. `/api/health` and `/api/catalog` state `demo-fixture` and their `db/seed.sql` source so a reader cannot mistake fixture state for the real database, and `/api/audit` returns the same typed `AuditSnapshot` the Connect profile serves rather than a second truth.
- The console is tokenized against `contract.md` v1.1.1. `_STYLE` declares the whole shared token table once per mode as `--atlas-*` custom properties under `:root[data-theme="light"]` and `:root[data-theme="dark"]`, and every rule below those two blocks resolves to a variable: no colour literal survives outside the token blocks, and switching mode is one attribute on `<html>`. `normalise_theme` accepts only `light` or `dark` and falls back to light for anything else, so an unusable `?theme=` value can never render an untokenized page, and the mode is explicit rather than read from the operating system. Links keep an underline so they never rely on colour alone, `:focus-visible` draws its outline from the focus token, and the open/bad order statuses, variant chips, the notice banner, and the journal rows use the four `state.*` pairs. The console still ships no external CSS, no JavaScript, and no new runtime import, so tokenizing it cost no dependency and no build step.
- The console is read-only and demo-only. There is no host knob, so it cannot be bound to a network; an unknown route is `404`, any other method is `405` with an `Allow` header, and an internal failure answers a generic `500` that leaks no detail. Responses carry `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that permits only the seed's image host, every interpolated value is HTML-escaped, and the document contains no script at all. Its state is `build_demo_business`: it registers the fixture items, receives the seed's one *received* purchase order, and posts three deterministic manual sales through the real `Business` methods, so the stock, sales, and journals on the page are the domain's own output, and the open purchase order stays genuinely open. All of it is rebuilt on every start and gone on exit; nothing is read from or written to a database and no peer is involved.
