## Implemented

- Python package with a local `core -> cluster -> plugin -> module` registry and no runtime third-party import on the standalone paths. The six baseline ERP clusters are seeded, and registrations and manifests are validated. `psycopg` is now a declared dependency, but it is imported only inside the two store adapters, so the package still imports and runs when the driver is absent.
- Process-local Atlas Connect kernel covering major-version handshake, manifest validation, share-only pairing, explicit `master`/`reader`/`proposer` authority, snapshots with opaque cursors, ordered deltas, idempotent inbox handling, and proposal transitions.
- In-memory `Business` domain for master items, purchase orders, receipts, and stock. Receiving an order once derives stock and rejects duplicate receipts; the local registry exposes `masterdata.items`, `purchasing.purchase_orders`, and `inventory.stock` without a peer.
- Local manual cash-sale flow that validates stock, decrements it, and records immutable `Sale`, `JournalEntry`, and `StockMovement` values. The journal is deliberately cash/revenue only: cash is debited and revenue is credited for the sale total. The local registry also exposes `sales.manual_sales` and `finance.journals` without a peer.
- `StockLevel` and `AuditSnapshot` are immutable, typed read projections over the item master, stock, sales, journals, and stock movements. The audit payload carries a typed item master (`item_id`, `sku`, `name`, `price_cents`) alongside the existing collections, so a peer can learn ERP-owned identity and price without a separate read. `Business.audit_snapshot()` orders items and stock by item ID, preserves recorded order for the other collections, and returns a point-in-time view that cannot observe later mutations; the projection remains in memory.
- `atlas_erp.connect_server` is a loopback-only HTTP profile: `GET /health` is public, while `GET /connect/manifest`, `GET /connect/audit`, and `POST /connect/sales` require a bearer token, and every route refuses a non-loopback peer. The token is scoped to a peer: `ATLAS_ERP_PEER_TOKENS` is a JSON object mapping a peer `app_id` to that peer's token, for example `{"atlas-erp": "<token>"}`, and the single-token `ATLAS_ERP_CONNECT_TOKEN` is gone rather than kept as an alias, because a token that names nobody cannot be held to a grant and a second peer would be impossible. The two guarded routes then ask the protocol module whether that peer may act, through `ROUTE_AUTHORITY`: `POST /connect/sales` asks for `sales.manual_sales:write` and `GET /connect/audit` asks for `audit.snapshot:read`, so a refusal is the module's `PermissionDeniedError` answered as `403 forbidden` rather than a decision this transport makes. `GET /connect/manifest` is deliberately grant-free and needs only a credential the transport knows, because a peer must be able to read the manifest before pairing and pairing is what grants authority. The manifest wire response normalizes permissions to a sorted flat array, and the audit response is a typed snapshot with a deterministic cursor.
- `POST /connect/sales` validates a bounded JSON body, checks every submitted `unit_price_cents` against the local item master (`400 price mismatch`), then calls the same `Business.create_manual_sale` path the local console would, so stock and journal invariants still hold. It never retries on the caller's behalf. The `201` response returns the posted sale, its journal ID, the resulting stock, and `journal_balanced`, so a peer can validate what it was handed without a second read. `409 insufficient stock` covers a stock conflict and `409 duplicate sale` covers a repeated `sale_id` rejected by the in-memory domain. Internal failures return a generic `500` and never leak detail.
- `atlas_erp.sale_store` is the durable idempotency layer for that one command. One `SaleCommandStore` protocol declares `reserve` / `complete` / `abort` / `close`, with two adapters: `InMemorySaleCommandStore` for tests and the loopback smoke, and `PostgresSaleCommandStore` for cross-process durability. The store owns exactly one table, `connected_sale_commands` (`sale_id` primary key, `request_hash`, a `status` check limited to `pending`/`completed`, a `response` jsonb receipt, `reserved_at`, `completed_at`). It is explicitly *not* an ERP state store, and it still is not one: it owns the receipt and nothing else. What it names used to be an incoherence, because the `Sale` it replays lived only in `Business._sales` — after a restart the receipt replayed a `201` naming a sale `/connect/audit` no longer listed and `stock_for` no longer reflected. The next bullet is what closed that, and this store is unchanged by it **apart from one thing the current slice added**: a **lease**. `DEFAULT_LEASE_SECONDS = 30` is how long one attempt may hold a `sale_id` before a later attempt for the same key may reclaim it — a loopback profile, where the window only has to outlast a slow in-flight call. A `pending` row older than the lease is reclaimable, and the reclaim is a single conditional `UPDATE … WHERE sale_id = %s AND status = 'pending' AND request_hash = %s AND reserved_at < now() - make_interval(secs => %s)`, of which **only `rowcount == 1` counts as winning it**, so two racers cannot both take over one crashed key. `SaleCommandReservation` gained `retry_after_seconds`, populated for `IN_PROGRESS` only, so a caller is told how long to wait instead of guessing whether a key is busy or stuck. **There is no way to turn the lease off and that is deliberate**: the old `lease_seconds=0` sentinel is gone, and a non-positive length is refused at construction by `_lease_seconds()`, which both adapters call before opening anything.
- `atlas_erp.business_store` is the durable layer for the business state a connected sale produces, and it mirrors `sale_store.py`'s shape deliberately rather than inventing a second one: a `BusinessStore` protocol (`ensure_schema` / `load` / `transaction` / `save_item` / `save_purchase_order` / `save_receipt` / `save_sale` / `save_movements` / `close`), an `InMemoryBusinessStore` for tests and the loopback smoke, a `PostgresBusinessStore` for cross-process durability, and a frozen `BusinessRecords` type whose field names are exactly `Business.restore`'s keyword arguments, so a load result is handed to the domain without reshaping. It owns **ten** tables: `master_items`, `sales` + `sale_lines`, `journal_entries` + `journal_lines`, `stock_movements`, and — since `9d4a2f5` — `purchase_orders` + `purchase_order_lines` and `receipts` + `receipt_lines`, so a reloaded domain now holds the records its stock movements came from. The same commit added `save_purchase_order` and `save_receipt` to the protocol and a `transaction()` context manager, which is how the boot seed became one unit of work: an interrupted first boot now leaves the store empty and the next boot re-seeds, rather than restoring a partial fixture as truth. **Purchasing is therefore no longer the partial lie it was** — a receipt's movements are stored beside the receipt that produced them. The current slice adds the database half of the purchasing validation: a `CHECK (state IN ('open', 'received'))` on `purchase_orders.state` and `CHECK (state IN ('received'))` on `receipts.state`, listing the same values as `PURCHASE_ORDER_STATES` and `RECEIPT_STATES` in `business.py` — repeated as a readable literal rather than interpolated, the way `sale_store`'s `status` check is written. **Those two `CHECK`s will not reach a database that already has the table, and that is recorded rather than papered over**: the `ponytail:` comment above the DDL says why. `ensure_schema` is `CREATE TABLE IF NOT EXISTS`, so a table created before these checks existed keeps its wider `text` column and never gains them. The honest name for that is a **missing migration runner** — a recorded undone item below — and the alternative, renaming the tables so `IF NOT EXISTS` misses them, would have thrown away real rows to buy a green schema. The comment is worth keeping for the reader who finds it: the constraint is right, and it is not yet true of any existing deployment. **Two rules make the round trip honest rather than merely plausible, and both are load-bearing.** *Order is stored, not derived*: the domain has no clock and no sequence of its own — `audit_snapshot` reports sales, journals, and movements in raw `dict` insertion order, which is process memory and nothing else — so every table carries a `bigserial seq` and `load()` reads `ORDER BY seq`. Ordering by business id instead would be wrong, and `tests/test_business_store.py` proves it with three sale ids (`…-sale-later`, `…-sale-audit`, `…-sale-json`) that no alphabetical sort reproduces. *No derived value is stored*: there is no stock column and no `total_debits_cents` column anywhere, because `stock_for` and `JournalEntry` totals re-derive from lines and a stored copy would drift from the lines it was copied from; the PostgreSQL test reads `information_schema` and asserts no such column exists and that every `*_cents` column is `bigint`. Money is integer cents in a `bigint` and never becomes a float. Table and column names are module-level literals, so no caller-supplied value ever reaches an identifier, and `psycopg` is imported function-locally so the package still imports without the driver — `PostgresBusinessStore` raises only when it is constructed. What remains true of this store is recorded at full length below rather than footnoted here: it is not atomic with the sale store, `save_item` has no production caller, and the schema it creates cannot be changed after the fact.
- `Business.restore(...)` is the single additive rehydration entry point, plus a module-level `_restored` helper that refuses to collapse a duplicate key instead of silently losing the record — the failure mode a rehydration path is most able to hide. `business.py` is **121 insertions and 0 deletions**, verified, so no existing signature, behaviour, or exception changed and every pre-existing test passes untouched. It repopulates the private dicts in the order it is given, because the order *is* the audit order; it rebuilds the two derived indexes `_items_by_sku` and `_receipts_by_order` rather than trusting them, since a reload that skipped them would lose SKU uniqueness and make `get_receipt_for_order` answer `None`; and it goes through the frozen dataclasses' own constructors so an invalid stored record fails loudly during reload instead of yielding a wrong number later, with nothing assigned until every record is built, so a rejected reload leaves the previous state intact. `_receipts_by_order` is derived from the receipts' own `order_id`, so it rebuilds even with no purchase order present. **The "through the constructors" clause above was, for purchasing lines, a claim nothing enforced, and the current slice found it.** It is recorded as written because the false version is the dangerous one: a reader would take a corrupt stored `PurchaseOrderLine` as already checked. `restore` passed the stored line objects straight to `PurchaseOrder`, whose `_purchasing_lines` only did an `isinstance` test, so a line that had been corrupted after its own constructor ran — which is exactly what a bad database row is — was accepted and moved stock by that number. `PurchaseOrderLine` now has a `__post_init__`, and `_purchasing_lines` rebuilds **every** accepted line through it rather than keeping it as it arrived, which is the only part of the check that closes the hole. The same commit added `__post_init__` to `PurchaseOrder` and `Receipt` (six such validators in `business.py` became nine) and the `PURCHASE_ORDER_STATES` / `RECEIPT_STATES` sets, so empty identifiers, empty `lines`, non-positive or non-integer quantities, and an out-of-set `state` are all refused at construction — and refused as the existing `BusinessError` subclasses rather than as a bare `ValueError`, because a reload path that raises a type its callers do not catch is a worse failure than the corrupt row. **The generalisable caution**: a docstring in the implementation had asserted this guarantee was already made, and no test covered it, and the assertion was false. A comment claiming an invariant is evidence of nothing; a test that fails when the invariant breaks is the whole value of the claim.
- `ConnectServer(..., business_store=...)` takes the second store optionally, as a trailing keyword defaulting to `None`, threaded through `_make_server` and `_ConnectHTTPServer`, so every existing caller is unaffected and `ConnectServer.close()` closes it alongside the sale store. `POST /connect/sales` writes the posted sale, its journal, and its movements through **before** `store.complete(...)` and inside the same `try`, so a store that cannot record the sale aborts the key and the peer is never handed a `201` for a sale no restart would still know about. The movements are read back off the domain rather than rebuilt, so the durable `movement_id`s are the ones the domain itself minted. The entry point reads the same `ATLAS_ERP_DATABASE_URL` on exactly the sale store's terms — blank or unset means in-memory, present-but-unusable is a startup failure naming the variable and never the DSN — and the banner now reports both modes, e.g. `sale receipts: postgres, business state: postgres`. The new helpers are `_sale_movements`, `_write_business_state`, `_business_store`, `_seed_business_store`, and `_startup_business`. `_startup_business` is where the restart actually happens: with no store it is the in-memory smoke fixture unchanged; with one, **stored state wins** — an empty store is seeded from the fixture once, and a populated store is restored instead of the fixture.
- `atlas_erp.web`, `atlas_erp.demo_catalog`, `__main__.py`, and `protocol.py` were **not touched** by this slice, and the constraint the console tests enforce on the first two (neither may contain `psycopg` or `sqlite`) still holds — the grep returns no match. The console therefore remains a demo-fixture reader by design, not by omission, and `web.py` is unaffected by the store's existence. `AuditSnapshot.to_dict()` still emits exactly the same five keys, so the wire contract with the React console and the content-hash cursor are both unchanged and the sibling `atlas-ecom` repository needs no change from this slice.
- `sale_command_hash` defines the identity of one connected sale command as a SHA-256 over the *validated* request (`customer_id`, `sale_id`, `lines`) serialized canonically, so JSON key order and insignificant whitespace do not change a command's identity while a different sale, customer, quantity, or price does.
- `CONNECTED_PEER_GRANTS` in `connect_server.py` is the one peer configuration this product ships: `atlas-ecom` gets `proposer` on `sales.manual_sales` and `reader` on `audit.snapshot`, and nothing else. **It is recorded debt rather than a design, and it is not the grant that keeps the connected checkout working, because no peer grant can**: one master per capability is the module's own rule, the serving app already holds every capability it serves, and `ProtocolKernel.grant` refuses a second master, so `sales.manual_sales:write` is reachable only by `atlas-erp` itself and a connected sale is answered `403 forbidden` for every peer. `proposer` is the role both product contracts already name for Ecom — it submits intent, ERP decides recognition, quantity, and value — so the row is that intent recorded, and the connected proposal flow is what makes it effective. `tests/test_connect_authority.py` pins both rows exactly, so the day they change is a deliberate edit.
- `ConnectServer(..., sale_store=...)` takes the store optionally. With one injected, `POST /connect/sales` reserves the `sale_id` before touching the domain and then completes it with the receipt: an identical retry replays the stored receipt and returns `201` without calling the domain again, the same `sale_id` with a different request is `409 sale id conflict`, an unfinished reservation is `409 sale in progress` **and now carries a `Retry-After` header holding the holder's lease**, and any failure between the two calls aborts the reservation so a rejected sale never burns its key. The `409` in-progress answer used to be the durable ceiling — *forever* — and that ceiling is what the lease fixed; the only reservation still not reclaimable is one held for a **different** request hash, because a live attempt for that hash may still own it, and releasing that stays a human decision through `abort`. With no store injected, behaviour is unchanged and the in-memory `409 duplicate sale` still applies.
- **Three implementation bugs the tests found, which are the most useful thing in this slice, because all three read as finished work.** Each one has a test that failed before its fix, and each is recorded with what it actually did rather than with the shape of the code around it:
  1. **The purchasing validation missed the exact case it was written for.** `Business.restore` hands stored `PurchaseOrderLine` objects to `PurchaseOrder`, and `PurchaseOrder`'s own check was an `isinstance` test, so `PurchaseOrderLine.__post_init__` was never re-entered and a corrupt stored quantity went straight through to stock. The validation was not wrong; it was in a place the reload path never went through. Fixed by rebuilding every accepted line through `PurchaseOrderLine` in `_purchasing_lines`.
  2. **`lease_seconds=0` did the opposite of what its own three comments said.** The check was `elapsed >= 0`, which is always true, so "0 disables the lease" did not disable exclusivity — it made *every* pending row instantly reclaimable, which hands one key to two live attempts at once. That is the single thing a reservation exists to prevent, and it was reachable from both adapters by one argument. Fixed by deleting the sentinel rather than by correcting the arithmetic, and by refusing a non-positive length at construction: **holding a claim forever was a recorded defect, not a capability, so there is nothing to switch back to.** The naive reading of `0` is zero seconds of exclusivity — the exact opposite of what it used to mean — and a reservation must not depend on a reader noticing that guard. Someone who wants a very long lease sets a very long number. The `_reclaimable` `> 0` special case and the "skip the reclaim when the lease is 0" branch were deleted as dead weight rather than left as a correct-by-accident guard, because a guard nobody can fail is a comment with extra steps.
  3. **`retry_after_seconds` never reached the caller.** `_RequestError` gained a `headers` attribute and `do_POST` dropped it on the floor, and the `409` was raised without it, so the wait hint existed in the store, in the reservation, and in a docstring claiming it was "in the standard place" — and on no wire anywhere. Fixed by threading `headers` through `do_POST` and `_send_json`, and the docstring claim was false when it was written.
- `ATLAS_ERP_DATABASE_URL` wires the durable stores in the `atlas_erp.connect_server` entry point: unset or blank keeps both in memory, a usable value creates both sets of tables and reports `sale receipts: postgres, business state: postgres`, and a configured-but-unusable database is a startup failure rather than a silent downgrade to a store that does not survive a restart. One variable, two stores over one URL, which is deliberate: they own different tables and merging them into one transaction is a later slice. Only the variable name is reported on failure, never the connection string. `psycopg` is declared in `pyproject.toml` but imported inside each adapter, so the package still imports when the driver is absent.
- `tests/cross_process_smoke.py` is a one-shot harness that starts one temporary ERP loopback server and then runs three Ecom clients against it: the read-only `connect:smoke`, the durable `connect:checkout-smoke` with `ATLAS_ERP_ALLOW_WRITE=1` (skipped with a printed reason when `ATLAS_ECOM_DATABASE_URL` is unset), and the lower-level `connect:order-smoke`. Child process cleanup is in `finally`. It is test infrastructure, not full pairing, full connected business operation, or production persistence.
- `python -m atlas_erp` standalone smoke entry point remains available and exercises purchasing -> stock and manual sale -> stock -> journal. The business and protocol state are process-local test infrastructure.
- `atlas_erp/demo_catalog.py` is the console's fixture: an immutable in-memory mirror of the committed `db/seed.sql` example catalogue (six items, 37 colour/size variants, one Unsplash placeholder image per variant, per-warehouse on-hand/reserved stock, two warehouses, two suppliers, two purchase orders) with the seed's own derived variant identity (`<SKU>-<COLOR>-<SIZE>`), plus `to_dict()` for the JSON route. It reads no table, and `tests/test_web.py` diffs it against the committed seed so a drift between fixture and seed fails the suite.
- `atlas_erp/web.py` is a server-rendered console built on the standard library only: no framework, no build step, no external CSS or JavaScript, and no new runtime import. `python -m atlas_erp.web` binds `127.0.0.1` on `ATLAS_ERP_WEB_PORT` (default `4311`, which leaves the Connect API on `4310` usable at the same time) and serves `GET /` as the HTML dashboard, plus `GET /api/health`, `GET /api/catalog`, and `GET /api/audit`. The dashboard is tiles, per-item catalogue cards with the variant table, stock by warehouse, purchasing, and the recent sales and general-ledger rows. `/api/health` and `/api/catalog` state `demo-fixture` and their `db/seed.sql` source so a reader cannot mistake fixture state for the real database, and `/api/audit` returns the same typed `AuditSnapshot` the Connect profile serves rather than a second truth.
- The console is tokenized against `contract.md` v1.1.1. `_STYLE` declares the whole shared token table once per mode as `--atlas-*` custom properties under `:root[data-theme="light"]` and `:root[data-theme="dark"]`, and every rule below those two blocks resolves to a variable: no colour literal survives outside the token blocks, and switching mode is one attribute on `<html>`. `normalise_theme` accepts only `light` or `dark` and falls back to light for anything else, so an unusable `?theme=` value can never render an untokenized page, and the mode is explicit rather than read from the operating system. Links keep an underline so they never rely on colour alone, `:focus-visible` draws its outline from the focus token, and the open/bad order statuses, variant chips, the notice banner, and the journal rows use the four `state.*` pairs. The console still ships no external CSS, no JavaScript, and no new runtime import, so tokenizing it cost no dependency and no build step.
- The console is read-only and demo-only. There is no host knob, so it cannot be bound to a network; an unknown route is `404`, any other method is `405` with an `Allow` header, and an internal failure answers a generic `500` that leaks no detail. Responses carry `X-Content-Type-Options: nosniff` and a `Content-Security-Policy` that permits only the seed's image host, every interpolated value is HTML-escaped, and the document contains no script at all. Its state is `build_demo_business`: it registers the fixture items, receives the seed's one *received* purchase order, and posts three deterministic manual sales through the real `Business` methods, so the stock, sales, and journals on the page are the domain's own output, and the open purchase order stays genuinely open. All of it is rebuilt on every start and gone on exit; nothing is read from or written to a database and no peer is involved.
- `frontend/` is the approved operator console frontend: a Vite 7 + React 19 + TypeScript 5.9 build with its own `package.json`, `package-lock.json`, TypeScript project references, `vite.config.ts`, and `src/`. It is a separate build, not a rewrite of `web.py`, and the Python package has no knowledge of it: no Python file changed for this slice, and `frontend/.gitignore` keeps `node_modules/`, `dist/`, and `*.tsbuildinfo` out of the tree, so the Node surface stays off the standalone import and test path the contract's risk section names. The two consoles can run at the same time on their own ports.
- The frontend reads three routes and sends nothing else. `src/lib/api.ts` holds the only `fetch` in the build: `fetchHealth`, `fetchCatalog`, and `fetchAudit` issue `GET /api/health`, `GET /api/catalog`, and `GET /api/audit` with an `accept: application/json` header, and no other method or path appears anywhere in `src/`. Every response is parsed against a Zod schema in `src/lib/schemas.ts`, and a refused connection, a non-2xx status, a non-JSON body, and a payload that no longer matches the schema each become one readable `ApiError` with a retry, so a panel degrades instead of rendering half-truths. There is no bundled fixture and no mock data in the app: with no API running, every panel shows that failure, which is the correct answer rather than a fallback dataset.
- `npm run dev` proxies `/api` to `http://127.0.0.1:4311` through `server.proxy` in `vite.config.ts`, so the browser sees a single origin while the Python console server stays bound to loopback. On the console itself, the remaining work is a write path, and the order still matters: only after the read surface is durable does a write button belong on the page, and it should go through the same `Business` methods the Connect profile already calls, behind an authenticated operator session with an audit record. Until the data is durable *on the surface being written to*, a browser action would only edit state that disappears, which is a worse demo than a read-only one — and that is still exactly the console's position, because the slice that added a durable store did not point this console at it. Two smaller obligations come with the fixture: `atlas_erp/demo_catalog.py` has to be updated in the same commit as any `db/seed.sql` change, because `tests/test_web.py` fails on drift, and the Unsplash links both consoles render are the same placeholders covered by the licensing review above. Tokenizing the page added no such obligation: the theme classes are part of the console's own markup and need no fixture change, and `ThemeTokenTests` fails if a future style edit reintroduces a colour literal outside the two token blocks. The frontend adds a third, on the other side of the wire: the Zod schemas in `src/lib/schemas.ts` are a *contract* with the Python payloads, so a field renamed, dropped, or retyped in `web.health_payload`, `DemoCatalog.to_dict`, or `AuditSnapshot.to_dict` turns into a panel that fails to parse rather than a wrong number, which is the right failure but a real one to keep in mind when changing a Python payload. The console test asserting that only GETs are sent is what keeps the read-only claim honest if a write is ever added.
